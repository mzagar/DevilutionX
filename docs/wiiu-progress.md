## Major findings

### 1. Cemu's `tweq` traps even when the condition is false (the big one)

**Symptom:** the game hangs at a specific point — the guest spins forever, the
OSReport log stops mid-line, Cemu stays alive at ~200 % CPU. Nothing crashes.

**Cause:** Cemu 2.6.0 implements `tweq` (conditional trap word, TO=EQ — "trap if
equal") incorrectly: it takes the trap *even when the registers are not equal*.
Cemu runs TW through its interpreter (`PPCInterpreter_TW` appears in `sample`
output — the JIT has no TW, so it falls back), and that handler is buggy.

**Why it hit us:** GCC emits `tweq` for libstdc++'s shared_ptr use-count
overflow guard, i.e. for

```cpp
if (old_use_count == 0x7FFFFFFF) __builtin_trap();
```

which is generated on **every `shared_ptr` copy**. So on Cemu, *any* shared_ptr
copy hangs the guest. In our case the first one happened inside
`LoadAudioFile()` → `SoundSample::SetChunk()`, which is why it looked like
"audio hangs".

**Proof chain:**

1. Markers narrowed the hang to `result.SetChunk(...)` for the first sfx
   (`sfx\items\titlemov.mp3`, 418 bytes) during `ui_sound_init()`.
2. A `std::atomic<int>` test printed `atomic test done val=1` → `lwarx`/`stwcx`
   atomics are fine, so it is not an atomicity problem.
3. Decisive test: `volatile int a = 5, b = 7; if (a == b) __builtin_trap();`
   printed `trap test begin` but never `trap test survived` → the trap fires
   with a false condition.
4. `objdump` confirmed the codegen is correct at that site:
   `lwz r10,104(r1)` (5), `lwz r9,32(r1)` (7), `tweq r10,r9`.

**Workaround:** [`tools/wiiu/cemu-tweq-workaround.py`](../tools/wiiu/cemu-tweq-workaround.py)
NOPs every `tweq` in the executable sections of `devilutionx.elf`. It finds 9
of them. Run it **after the build and before `elf2rpl`**, and re-run it after
every rebuild (the ELF is regenerated).

The NOP'd guard is an unreachable overflow check (it could only fire after
2^31−1 copies of one control block), so patching is behaviour-neutral — the
patched binary is still correct on real hardware, and a single artifact can be
used for both. Drop the workaround once Cemu fixes `tweq`.

### 2. Lua needs `LUA_USE_C89` on PowerPC

Without it, Lua panics with `attempt to index a nil value` during
`LuaInitialize`. Fixed in `3rdParty/Lua/CMakeLists.txt` by adding `WIIU` to the
`LUA_USE_C89` platform list (next to 3DS, Vita, Switch, NXDK).

### 3. Input: it was a Cemu *settings* problem, not a code problem

The menu was unresponsive until the host keyboard was mapped to
**Controller 1 → GamePad** in Cemu's input settings (arrows → D-pad,
Enter/`4` → A). No `VPADInit`/`KPADInit` calls were needed — SDL's Wii U
backend handles that.

### 4. The system swkbd confirm button is broken on Cemu

`SDL_StartTextInput()` launches the Wii U system keyboard, whose ✓ button does
not close the dialog on Cemu 2.6 macOS. `Source/platform/wiiu/keyboard.cpp`
therefore skips swkbd entirely and just enables `SDL_TEXTINPUT`, letting the
normal `UiEdit` event loop (in `Source/DiabloUI/diabloui.cpp:228`) handle
Enter/Backspace like the PC version.

### 5. `elf2rpl` needs an unstripped ELF

`powerpc-eabi-strip` removes the `.rela.*` sections that `elf2rpl` needs, and
fails with `renameRplWrap failed`. The strip step is disabled by patching the
generated `build.make`. This is **lost on every `cmake` re-run**, so
`tools/wiiu/wiiu-run.sh` re-applies it automatically.

### 6. OSReport's printf does not support length modifiers

`%zu` and `%lu` print *nothing* **and swallow the trailing `\n`**, so two log
messages end up glued on one line. Always use `%d` / `%x` / `%s` with explicit
casts (e.g. `static_cast<int>(v.size())`).

### 7. Line endings: the repo uses `* -text` and many files are CRLF

`.gitattributes` sets `* -text`, so git never converts line endings — and a
number of upstream files (including `Source/engine/sound.cpp`) are committed
with **CRLF**. Editing those files with tools that normalize to LF produces a
whole-file diff. Convert back to CRLF before committing, or keep the editor
from rewriting the file.

### 8. SDL2 for Wii U has no filesystem backend

`libSDL2.a` for Wii U is built with the **dummy** filesystem backend. Verified by
disassembling the object file:

```bash
cd /tmp && mkdir sdl2x && cd sdl2x
/opt/devkitpro/devkitPPC/bin/powerpc-eabi-ar x /opt/devkitpro/portlibs/wiiu/lib/libSDL2.a
/opt/devkitpro/devkitPPC/bin/powerpc-eabi-objdump -dr SDL_sysfilesystem.o
```

Both functions are three instructions: `SDL_Error(SDL_UNSUPPORTED)` (code 4)
and `return NULL`. So on Wii U **`SDL_GetBasePath()` and `SDL_GetPrefPath()`
always return NULL**, and `Source/utils/paths.cpp` silently falls back to the
generic `#else` branch:

| Function | Value before the packaging fix |
|----------|-------------------------------|
| `BasePath()` | `""` |
| `AssetsPath()` | `"assets/"` |
| `PrefPath()` / `ConfigPath()` | `""` |

That is why the game used to work only when the CWD happened to be the SD card
root, and why it wrote saves and `diablo.ini` next to the game data. Nothing is
broken in SDL — the Wii U port simply never implemented these two calls, so the
port has to resolve its paths itself (`Source/platform/wiiu/init.cpp`).

### 9. Real hardware (Aroma) verified on 7 Nov 2026

The packaged WUHB was run on a real Wii U under Aroma, launched from
`sd:/wiiu/apps/devilutionx/`. **Everything works** — boot, rendering, input,
audio, gameplay, and save/load.

The open question was whether Aroma mounts the WUHB content the way Cemu does.
It does. `boot-diag.txt` from the hardware boot:

```

  -- volumes --

  content/assets               '/vol/content/assets' -> YES

  sd data dir (ours)           '/vol/external01/wiiu/apps/devilutionx' -> YES
```

**Hardware vs Cemu — everything that differs:**

| | Cemu 2.6.0 | Real Wii U (Aroma) |
|---|---|---|
| `/vol/content` content mount | YES | **YES** — same |
| `/vol/save` | does **not** exist | **exists and is writable** |
| `listdir '/vol'` | works (`storage_mlc01`, `content`, `external01`) | **FAILED** |
| CWD, NULL SDL paths, all 4 resolved paths | — | **identical to Cemu** |

- **`/vol/save` exists on hardware.** It is the per-title save volume, and Aroma
  redirects it to `sd:/wiiu/apps/save/B12DEFFB (DevilutionX)/` (with the usual
  `common/` + `80000001/` subdirectories, both left empty). So the WUHB *does*
  get a title ID — `B12DEFFB` — even though `wuhbtool` has no flag for one; it is
  derived from the RPX. The port does not use this volume: data still goes to
  `sd:/wiiu/apps/devilutionx/`. See [Next steps](#next-steps) if we ever want
  saves to live in the title's save data instead.
- **`listdir '/vol'` fails on hardware** while it succeeds on Cemu. Harmless —
  it is only used for the diagnostic listing, and every specific path the port
  actually probes (`/vol/content`, `/vol/external01`, `/vol/save`) reports
  correctly. `EnsureDir()` already tolerates the same kind of EIO on virtual
  volume roots.
- Everything else is byte-for-byte the same as Cemu, which is exactly why one
  artifact serves both.

**End-to-end confirmation:** the game created
`sd:/wiiu/apps/devilutionx/diablo.ini` by itself, and grew the migrated save
(`spawn_1.sv`, 202,444 → 299,956 bytes) after a play + save cycle — so config
writing, saving and loading are all confirmed on hardware, not just on Cemu.

### 10. Full game + Hellfire data

The shareware `spawn.mpq` is bundled inside the WUHB, so the port boots with no
extra files. The **full game and the Hellfire expansion also work** — verified
on Cemu on 7 Nov 2026.

**Where the MPQs go.** `GetMPQSearchPaths()` (`Source/engine/assets.cpp:441`)
builds its list from `paths::BasePath()`, `paths::PrefPath()` and
`paths::ConfigPath()` (dropping duplicates) and then appends the CWD. On Wii U
that resolves to:

1. `/vol/content/assets/` — read-only, inside the WUHB
2. `/vol/external01/wiiu/apps/devilutionx/` — our data directory
3. `""` — the CWD, `fs:/vol/external01`, i.e. the SD card root

So the retail MPQs belong in the data directory next to the WUHB. `LoadMPQ()`
tries `<path>DIABDAT.MPQ` first, then `diabdat.mpq`, and only falls back to
`spawn.mpq` when neither exists — the bundled shareware therefore stays a
harmless fallback rather than being shadowed.

**Getting them.** The GOG "Diablo + Hellfire" installer
(`setup_diablo_1.09_hellfire_v4_(78466).exe`, 850 MB) is an **Inno Setup 5.6.2**
archive. `tools/wiiu/extract-gog-mpqs.sh` pulls out the five files we need:

| File | Size |
|------|------|
| `DIABDAT.MPQ` | 517,501,282 B |
| `hellfire.mpq` | 65,502,336 B |
| `hfmonk.mpq` | 37,658,368 B |
| `hfmusic.mpq` | 34,379,360 B |
| `hfvoice.mpq` | 37,743,520 B |

Not needed: `Patch_rt.mpq` — DevilutionX applies its own fixes and never reads
it (there is no reference to it anywhere in `Source/`) — nor
`DRTL_IX86_108_109.mpq`, the 1.08→1.09 patch, which is already applied.
`hfbard.mpq`/`hfbarb.mpq` are Bard/Barbarian extras that GOG does not ship, so
`HaveBardAssets`/`HaveBarbarianAssets` are simply false.

**Two gotchas on the way:**

- **Homebrew's `innoextract` is a trap.** It depends on `boost`, which has no
  bottle for this Homebrew, so `brew install innoextract` builds boost from
  source — the better part of an hour (and an interrupted attempt leaves a
  `boost …tmp` keg behind). Running `innoextract` inside a throwaway Debian
  Docker container takes about two minutes, which is what the script does when
  `innoextract` is not on `PATH`.
- **Do not try to carve the MPQs out of the installer by scanning for the
  `MPQ\x1a` magic.** It is tempting — the installer contains seven occurrences —
  but they are all false positives inside the compressed data. The proper check
  is to decrypt the hash table with `HashString("(hash table)", 3)` and look up
  a known file name; every naive candidate fails it (their block tables claim
  extents of 6–8 GB inside an 850 MB file).

**Verification.** With the MPQs in place, a temporary `DBG` line after
`LoadGameArchives()` in `Source/diablo.cpp` reports:

```
DiabloMain: gbIsSpawn=0 HaveIntro=1 HaveHellfire=1 HaveBardAssets=0
```

- `gbIsSpawn=0` — `DIABDAT.MPQ` was loaded, so this is the full game
- `HaveIntro=1` — `gendata\diablo1.smk` exists, i.e. **the intro cinematic only
  exists in the full game**. Shareware shows the Blizzard logo and goes straight
  to the menu; the code even special-cases it, `menu.cpp` does
  `if (gbIsSpawn && !HaveIntro()) done = false;`, which is why "Replay Intro"
  does nothing there
- `HaveHellfire=1` — `hellfire.mpq` was found (`HasHellfireMpq` is set by
  `FindMPQ(paths, "hellfire")` in `LoadCoreArchives()`)

**Diablo vs Hellfire** — a first approximation is the `Game` key in `diablo.ini`
(`StartUpGameMode`: `Ask=0`, `Hellfire=1`, `Diablo=2`). It is
`OptionEntryFlags::Invisible` in `Source/options.cpp`, so it does **not** appear
in the settings menu. With `Ask` and the Hellfire MPQs present, `DiabloInit()`
calls `UiSelStartUpGameOption()` (`Source/diablo.cpp:1301`), which shows an
*Enter Hellfire* / *Switch to Diablo* dialog and saves the choice. `Hellfire` is
migrated to `Diablo` plus `Mods.SetHellfireEnabled(true)`.

But `Game` is only the *prompt*: what actually enables the expansion is the
`hf` entry it writes in `[Mods]` — see
[finding 11](#11-the-hellfire-expansion-is-a-lua-mod-not-game-data). Having the
MPQs is not enough.

### 11. The Hellfire expansion is a Lua *mod*, not game data

Having the Hellfire MPQs is **not** enough to play Hellfire. In this version of
DevilutionX the expansion is implemented as a **mod**, and `gbIsHellfire` is
flipped by Lua alone:

```lua
-- mods/hf/lua/mods/hf/init.lua
local hellfire = require("devilutionx.hellfire")
hellfire.loadData()   -- LoadHellfireArchives(): hellfire.mpq, hfmonk/hfmusic/hfvoice
hellfire.enable()     -- gbIsHellfire = true
```

`Source/lua/modules/hellfire.cpp` exposes exactly that pair, and
`LuaReloadActiveMods()` (`Source/lua/lua_global.cpp:255`) **resets
`gbIsHellfire = false`** before loading mods, so nothing else can turn it on.

`mods/hf/` is 24–25 files that live **in this repository** (tracked in git), so
the port ships it; `CMake/Mods.cmake` lists them and either copies them loose or
— with `BUILD_ASSETS_MPQ=ON` — packs them into `hf.mpq`.

**The failure mode is silent.** `Source/lua/lua_global.cpp:261`:

```cpp
for (const std::string_view modname : modnames) {
    const std::string packageName = StrCat("mods.", modname, ".init");
    RunScript(CreateLuaSandbox(), packageName, /*optional=*/true);
}
```

`optional=true` means a missing mod is only logged at info level — which never
reaches Cemu's `log.txt`, since that only carries OSReport — and the game
carries on. The symptom is therefore very misleading: `hellfire.mpq` is present,
`HaveHellfire=1`, the *Enter Hellfire* dialog appears, everything looks right —
and the class list still offers only Warrior/Rogue/Sorcerer, with no Monk and no
Hive or Crypt.

**Where the mod is looked for** (`LoadModArchives()`,
`Source/engine/assets.cpp:703`):

| Form | Location |
|------|----------|
| loose directory | `<PrefPath>/mods/hf/` or `<BasePath>/mods/hf/` |
| packed MPQ | `<MPQ search path>/mods/hf.mpq` |

`[Mods] hf=1` in `diablo.ini` only says *enabled* — the files still have to be
findable. `DiscoverMods()` (`Source/options.cpp:72`) adds `hf` to the known mod
names whenever `HaveHellfire()` is true, which is why that ini key appears by
itself as soon as `hellfire.mpq` is on the card.

#### Packed, not loose — it changes the save namespace

`hf.mpq` must be a **packed MPQ**, not a loose directory, or Hellfire silently
shares its character files with Diablo.

`GetSaveExtension()` (`Source/pfile.cpp:74`) asks
`GetActiveModSaveExtension()` (`Source/mods/mod_identity.cpp:164`), which walks
the registered mod identifiers and picks up any `saveExtension` from a mod's
manifest. `mods/hf/manifest.ini` declares `saveExtension=hsv`.

But a **loose** mod never gets an identifier at all: in `LoadModArchives()` only
the packed branch calls `RegisterPackedModIdentifier()` +
`ReadLoadedModManifest()`; a loose mod just sets `hasLooseOverride[i]` and falls
through both branches. Its manifest is therefore never consulted and the
extension stays `sv`.

| Form | Save extension | Character files |
|------|----------------|-----------------|
| loose `mods/hf/` | `sv` | shared with Diablo (`single_*.sv`) |
| packed `mods/hf.mpq` | `hsv` | Hellfire-only (`single_*.hsv`) |

`tools/wiiu/build-hf-mpq.sh` builds the MPQ. `smpq` is not in the devkitPro
repos and Homebrew has no formula, but Ubuntu's `universe` has it, so the script
installs it into a small cached Docker image (override with
`WIIU_DOCKER_IMAGE`). It takes the file list from `CMake/Mods.cmake` so the
archive matches what upstream builds — 24 files, deliberately excluding
`txtdata/sound/effects-unused.tsv`, which is not in that list.

`tools/wiiu/package-wuhb.sh` stages the result as `assets/mods/hf.mpq` **inside
the WUHB**. Since `<BasePath>` is `/vol/content/assets/`, the game finds it
there and **the SD card needs no `mods/` directory at all**.

### 12. Diablo and Hellfire saves are not interchangeable

A save file is `<PrefPath>/<prefix><n>.<ext>`, and **both** parts encode which
game the character belongs to (`Source/pfile.cpp:81`):

```cpp
gbIsSpawn ? (gbIsMultiplayer ? "share_" : "spawn_")
          : (gbIsMultiplayer ? "multi_" : "single_"),
saveNum, ".", ext
```

- prefix — shareware (`spawn_`/`share_`) vs full game (`single_`/`multi_`)
- extension — Diablo (`sv`) vs Hellfire (`hsv`), see
  [above](#packed-not-loose--it-changes-the-save-namespace)

So a shareware character (`spawn_1.sv`) stays invisible after switching to the
full game. That one is easy to fix: only the prefix differs, so renaming
`spawn_1.sv` to `single_1.sv` brings the character across.

**Diablo ⇄ Hellfire is different: it genuinely does not work.** The names
*inside* the save archive depend on how many dungeon levels the current game has
(`Source/pfile.cpp:227`):

```cpp
bool GetFileName(uint8_t lvl, char *dst)
{
    if (GetPermSaveNames(lvl, dst)) return true;
    if (lvl == giNumberOfLevels * 2)     { memcpy(dst, "game", 5); return true; }
    if (lvl == giNumberOfLevels * 2 + 1) { memcpy(dst, "hero", 5); return true; }
}
```

with `giNumberOfLevels = gbIsHellfire ? 25 : 17` (`Source/loadsave.cpp:2728`) —
17 levels for Diablo, 25 for Hellfire.

Observed when `single_0.sv` was copied to `single_0.hsv`: the character **did**
show up in Hellfire, with a working *Load Game* option, but clicking it rewrote
the archive under Hellfire's name set and then failed with *"Unable to open save
file archive"*. The file went from 387,243 to 265,417 bytes, and `smpq -l`
showed the same nine data blocks at the same sizes, but sitting in different
hash slots — i.e. renamed. The entry the game then looks for (`game`) no longer
exists under that name, because in Hellfire's numbering it has moved.

**Play Hellfire with a fresh character; leave Diablo saves alone.** That is
precisely what the separate namespace is for. (The original was never at risk —
only the copy was damaged.)

### 13. The intro cinematic option is consumed even when the movie is missing

`[StartUp] Diablo Intro` is `StartUpIntro { Off = 0, Once = 1, On = 2 }`,
defaulting to `Once`. In `DiabloSplash()` (`Source/diablo.cpp:1330`):

```cpp
if (*intro != StartUpIntro::Off) {
    play_movie(gbIsHellfire ? "gendata\\Hellfire.smk" : "gendata\\diablo1.smk", true);
    if (*intro == StartUpIntro::Once) {
        intro.SetValue(StartUpIntro::Off);
        if (!demo::IsRunning()) SaveOptions();
    }
}
```

`play_movie()` returns `void` and reports nothing when the asset is missing — and
`gendata\diablo1.smk` is **not in the shareware data**. So playing the shareware
marks the intro as seen. Buy the game afterwards and the intro never plays,
because `diablo.ini` already says `Diablo Intro=0`.

Fix: set `Diablo Intro=1` (play once, then it turns itself off) or `2` (play
every boot). Neither value is in the settings menu — the enum deliberately hides
`Once` and exposes only OFF/ON. `Splash=2` is what shows the Blizzard logo
before it.

The same applies to `Hellfire Intro`, and there is a third way to see the
cinematic: leaving the main menu idle for 30 seconds triggers attract mode,
which plays it again (`Source/DiabloUI/mainmenu.cpp:120`).

## Build pipeline

```bash
cd build-wiiu-release

# 1. Build (strip must be disabled first — see finding 5)
make -j4

# 2. Cemu workaround — MUST run before elf2rpl (see finding 1)
python3 ../tools/wiiu/cemu-tweq-workaround.py devilutionx.elf

# 3. Pack the Hellfire mod (see finding 11). Only needed when mods/hf changes —
#    it lands in build-wiiu-release/mods/hf.mpq and is then staged into the WUHB.
../tools/wiiu/build-hf-mpq.sh

# 4. Convert + package as a self-contained Aroma-layout WUHB
../tools/wiiu/package-wuhb.sh        # elf2rpl + wuhbtool --content

# 5. Run
"/Applications/Cemu.app/Contents/MacOS/Cemu" \
  -g "$PWD/devilutionx.wuhb" -m /Users/mario/work/wiiu/cemu-mlc
```

All of this is wrapped by `tools/wiiu/wiiu-run.sh`.

> `NOSOUND`/`NONET` were passed as `-D…` on the original `cmake` command line,
> so they are stored in `CMakeCache.txt` as `UNINITIALIZED` and a platform-file
> change alone does not override them. Reconfigure with `-DNOSOUND=OFF` (or
> delete the cache) when changing these.

### Audio

The devkitPro SDL2 Wii U port ships a real AX audio driver (`SDL_wiiuaudio.c`,
`WIIUAUDIO_*`, `AXInitWithParams`/`AXAcquireVoice`), so no extra platform init
was needed. DevilutionX uses the bundled static SDL_audiolib
(`3rdParty/SDL_audiolib`). Confirmed at runtime:

```
Aulib::init done rate=22050 channels=2 frameSize=2048 format=9010
```

Cemu's AX emulation feeds the host via Cubeb.

dialog, and it warns if `hf.mpq` is absent (the WUHB would simply have no
Hellfire support).

## Runtime layout

### Path resolution

`Source/platform/wiiu/init.cpp` resolves everything by hand, because SDL gives
us nothing on Wii U (see [finding 8](#8-sdl2-for-wii-u-has-no-filesystem-backend)).
`wiiu_init()` runs before `DiabloMain()` and does two things: log the
environment, then set the paths.

**Assets** — if `/vol/content/assets` exists (i.e. the WUHB was packaged with
`--content`), it is used; otherwise the historical CWD-relative layout is kept:

| Layout | `BasePath()` | `AssetsPath()` |
|--------|--------------|----------------|
| WUHB (`/vol/content/assets` exists) | `/vol/content/assets/` | `/vol/content/assets/` |
| Plain SD card (fallback) | `""` | `"assets/"` |

> `BasePath()` and `AssetsPath()` are the same directory in the WUHB layout
> because `spawn.mpq` lives inside `assets/`. The MPQ lookup
> (`GetMPQSearchPaths()` in `Source/engine/assets.cpp`) only searches
> `BasePath()`/`PrefPath()`/`ConfigPath()`/CWD, so the alternative would be
> duplicating the 24 MB MPQ at the content root.

**Writable data** — `/vol/external01/wiiu/apps/devilutionx/` is created on first
run (recursively, then verified with a real write+delete probe, because
`access()` is unreliable on FAT) and used for both `PrefPath()` and
`ConfigPath()`:

| What | Where |
|------|-------|
| `diablo.ini` | `<data dir>/diablo.ini` |
| Savegames | `<data dir>/save_*.sv` |
| Mods, demos, screenshots | `<data dir>/…` |

If the data dir cannot be created or written to, both paths fall back to `""`
(CWD).

`wiiu_log_paths()` is also called from `Source/diablo.cpp` after
`ApplicationInit()` and dumps the four resolved paths plus a probe of
`/vol/save`, so the log always shows which layout was picked.

> **`/vol/save` is deliberately unused.** It exists and is writable on real
> hardware, but *not* on Cemu, so depending on it would break the Cemu
> development loop. See [finding 9](#9-real-hardware-aroma-verified-on-7-nov-2026)
> and [Next steps](#next-steps).

Everything `wiiu_init()` reports is additionally written to
[`boot-diag.txt`](#boot-diagnostics-boot-diagtxt) on the SD card, which is the
only way to see it on real hardware.

### Layouts on disk

**WUHB (Aroma / Cemu, the shipped artifact):**

```
devilutionx.wuhb
└── /content/assets/…            read-only, mounted at /vol/content/assets
    ├── spawn.mpq                shareware fallback
    ├── fonts/, data/, ui_art/…
    └── mods/hf.mpq              the Hellfire mod, packed (finding 11)

sd:/wiiu/apps/devilutionx/       writable, created on first run
├── devilutionx.wuhb             on the real card (this is what Aroma launches)
├── DIABDAT.MPQ                  retail base game
├── hellfire.mpq + hf*.mpq       retail Hellfire data
├── diablo.ini
├── single_0.sv                  one per character (Diablo)
├── single_0.hsv                 Hellfire characters, separate namespace
├── stash.sv
└── boot-diag.txt                rewritten on every boot
```

Note there is **no `mods/` directory on the SD card** — the mod is inside the
WUHB. `diablo.ini` and the saves are the only things the game creates.

**Plain SD card (dev builds, no content mount):**

```
sd:/
├── devilutionx_sd.wuhb (or .rpx via a loader)
├── assets/…                 ← legacy, still supported
└── wiiu/apps/devilutionx/   ← writes always land here now
```

## Debug logging (OSReport)

The debug output is deliberately **kept in the tree** — it is the main debugging
tool for this port and will be needed again. It shows up in Cemu's log as
`[OSConsole]`.

```cpp
#ifdef __WIIU__
#include <coreinit/debug.h>
#define DBG(fmt, ...) OSReport("Tag: " fmt "\n", ##__VA_ARGS__)
#else
#define DBG(fmt, ...) ((void)0)
#endif

DBG("value = %d", static_cast<int>(x));
```

Current instrumentation:

| File | Macro | Purpose |
|------|-------|---------|
| `Source/diablo.cpp` | `DBG` | `DiabloInit` step markers |
| `Source/lua/lua_global.cpp` | `DBG` | `LuaInitialize` step markers |
| `Source/platform/wiiu/init.cpp` | `Diag()` | Environment dump + resolved paths (also written to `boot-diag.txt`) |
| `Source/engine/sound.cpp` | `SND_DBG` | Audio load / `Aulib::init` tracing |
| `Source/utils/soundsample.cpp` | `SMPL_DBG` | `SoundSample::SetChunk` tracing |
| `Source/effects.cpp` | `SFX_DBG` | SFX load tracing (per-file — verbose, slows loading) |

`Source/engine/sound.cpp` additionally contains two throwaway test blocks (an
`std::atomic` test and a `__builtin_trap` test) that were used to prove the
`tweq` finding. They are dead weight now and are kept only because the port is
still being debugged actively. Remove them before any upstream PR.

> Cemu's `log.txt` is **rewritten** on every run, not appended — don't compare
> line counts between runs.

### Boot diagnostics (`boot-diag.txt`)

OSReport is **not visible on real hardware** without extra tooling (UDP logger,
serial), so `wiiu_init()` mirrors everything it reports into a file on the SD
card:

```
sd:/wiiu/apps/devilutionx/boot-diag.txt     (fallback: sd:/boot-diag.txt)
```

The fallback is used when the data directory cannot be created (e.g. write-
protected SD card), and is the reason the file's own path is printed as the last
line. The file is **overwritten on every boot**.

In `init.cpp` the `DBG` macro is therefore replaced by `Diag()`, which both
`OSReport`s and appends to a buffer; `DiagFlushToSd()` writes that buffer out. It
is called from `wiiu_log_paths()`, i.e. once during `wiiu_init()` and once after
`ApplicationInit()` — so a boot that dies later still leaves a file behind.

This is the primary hardware bring-up tool: if the game does not start on a real
Wii U, this file says whether the content mount was available, which paths were
picked, and whether the SD card is writable.

Verified on Cemu both ways: with a content mount, and with `devilutionx.rpx` run
directly (no content) — the latter correctly reports
`content mount '/vol/content' -> no`, `listdir '/vol/content' -> FAILED` and the
CWD-relative fallback paths, while still writing the file.

## Pitfalls

| Symptom | Cause / fix |
|---------|-------------|
| Guest hangs mid-load, log stops, Cemu alive at high CPU | Cemu `tweq` bug — run `tools/wiiu/cemu-tweq-workaround.py` before `elf2rpl` |
| `elf2rpl` → `renameRplWrap failed` | Strip must be disabled in `build.make` before converting |
| Lua panic `attempt to index a nil value` | `LUA_USE_C89` missing for WIIU in `3rdParty/Lua/CMakeLists.txt` |
| Menu does not react at all | Cemu input settings: map keyboard → Controller 1 (GamePad) |
| Text input ✓ button does nothing | swkbd broken on Cemu; `keyboard.cpp` bypasses it |
| Assets not found | Either `/vol/content/assets/spawn.mpq` (WUHB layout) or `./assets/spawn.mpq` (SD layout) must exist; see [Path resolution](#path-resolution) |
| Game writes saves/`diablo.ini` to the SD root | Running a WUHB that was packaged **without** `--content`, so the content mount is empty and the fallback layout is used |
| WUHB boots to "MPQ file(s) might be damaged" | Packaged without `--content`, or the assets dir had no `spawn.mpq` |
| `mkdir '/vol' failed (errno=5)` | Harmless — `/vol` is a virtual volume root; `EnsureDir()` ignores it |
| Hellfire MPQs present, `hf=1`, dialog appears — but only 3 classes, no Monk | The `hf` **mod** is missing. `RunScript(..., optional=true)` fails silently. Check that `assets/mods/hf.mpq` is inside the WUHB (finding 11) |
| Hellfire characters land in `single_*.sv`, shared with Diablo | Mod was loaded as a loose directory instead of a packed `hf.mpq`, so `saveExtension=hsv` is ignored — see [finding 11](#packed-not-loose--it-changes-the-save-namespace) |
| *"Unable to open save file archive"*, save shrinks | A Diablo save was copied to `.hsv` (or vice versa). The two namespaces are not interchangeable — see [finding 12](#12-diablo-and-hellfire-saves-are-not-interchangeable) |
| Intro cinematic never plays although `HaveIntro=1` | `Diablo Intro=0` — `Once` was consumed while playing shareware, which has no `diablo1.smk` — see [finding 13](#13-the-intro-cinematic-option-is-consumed-even-when-the-movie-is-missing) |
| Two log lines glued together | OSReport printf: don't use `%zu` / `%lu` |
| Whole-file diff after editing | File is CRLF in git; don't let the editor rewrite endings |
| Black screen, no errors | Missing `assets/ASSETS_VERSION` (fails the version check) |
| Game does not start on real hardware | Read `sd:/wiiu/apps/devilutionx/boot-diag.txt` first — see [Boot diagnostics](#boot-diagnostics-boot-diagtxt) |

## Next steps

1. **Clean up** — the cheapest thing standing between this and an upstream-able
   branch. Deliberately deferred: the debug instrumentation stays until the next
   feature is implemented, because it is the main tool for debugging it:
   - the throwaway `tweq` test blocks in `Source/engine/sound.cpp` (an
     `std::atomic` test and a `__builtin_trap` test)
   - the per-file `SFX_DBG` spam in `Source/effects.cpp` — it slows sound
     loading and floods the log
   - `Source/platform/wiiu/stub.cpp` — unused, still listed in
     `Source/platform/wiiu/CMakeLists.txt`
   - the CRLF-only churn in the top-level `CMakeLists.txt` (real change is just
     the `if(WIIU)` block)
   - the now-redundant `-DLUA_USE_C89` in `CMake/platforms/wiiu.cmake` (the fix
     lives in `3rdParty/Lua/CMakeLists.txt`)
   - the temporary `gbIsSpawn=… HaveIntro=… HaveHellfire=…` `DBG` line in
     `Source/diablo.cpp` (added for [finding 10](#10-full-game--hellfire-data))
2. **Next feature — undecided, to be brainstormed.** Candidates on the table:
   - **Local multiplayer on one Wii U.** Three shapes were proposed: (a)
     split-screen, 2–4 players, each with their own controller (Mario Kart
     style); (b) 2–4 players sharing a single screen, so nobody can wander off
     alone; (c) a hybrid — one shared screen while the party is together, which
     splits when a player walks away, the others carrying on in the shared view.
   - **Network multiplayer** (`NONET=OFF` + `nsysnet` init, mirroring
     `Source/platform/switch/network.cpp`). Note the test SD card already has the
     `Inkay-pretendo` module and plugin installed, which may matter for testing.
   - **Polish**: `DEVILUTIONX_GAMEPAD_TYPE Nintendo`, TV/DRC docking handling
     (Switch has `docking.cpp`), HOME/ProcUI integration.
3. **Decide on `/vol/save`** for `PrefPath()`/`ConfigPath()`. It is the "proper"
   per-title save volume and works on hardware, but it does **not** exist on
   Cemu, so using it would need the current SD path kept as a fallback. The SD
   path works, is easy to inspect from a card reader, and survives a
   reinstall — this is a correctness-vs-convenience call, not a bug.
